# solution-spec.yaml → Power Automate legacy package

<!-- v1.0.0 -->

Reads `flows[]` and `lists[]`. Ignores every other section.

Rules are tagged `PLATFORM` (observed in a real export or generated by the platform) or `HOUSE`.
See `docs/EVIDENCE-TIERS.md`.

## Step 0 — Get a template export. Nothing works without one.

**Ask for a real `.zip` exported from the target tenant before generating anything.** Any flow
will do — the simplest possible one. If the user has none:

> Power Automate → **Create** → **Automated cloud flow** → any trigger → one action → Save.
> Then **My Flows → ⋯ → Export → Package (.zip)**. Two minutes.

**Why this is not optional.** A package carries values that cannot be derived, guessed, or looked
up: per-connection identifiers, resource GUIDs, and tenant identifiers. They are opaque strings
belonging to that tenant. A package built without them imports to a grey connection X and
`PackageFlowMissingConnectionMap`.

The template supplies the *shell*. Only `definition.json`'s `triggers` and `actions` are
regenerated. Everything else is carried verbatim.

**One warning to pass on:** an export embeds the exporting user's email address and the tenant's
GUIDs in plain text. Every package generated from it carries them. Say so before the user shares
a package outside the organisation.

## Workflow

1. **Take the template export**, unzip it, and read its structure. `scripts/inspect_package.py`
   prints it.
2. **Read `flows[]`** from the spec. One package per flow — legacy packages hold one flow.
3. **Build the definition** — triggers and actions, per `references/wdl-schema.md`.
4. **Carry everything else verbatim** — both manifests, both map files, `connectionReferences`,
   `definition.metadata`.
5. **Check the connectors match.** If the spec needs a connector the template does not have, stop:
   the template cannot supply its connection identifiers. Ask for an export that uses it.
6. **Build the zip** — `python scripts/build_package.py <spec> <flow-id> --template <export.zip>`.
7. **Validate.** See the gate below.
8. **Tell the user what to expect at import** — see the rule on the connection prompt.
9. **Offer the capture step** once the flow imports and runs.

### Checklist

```
[ ] a real export from the target tenant is in hand
[ ] all five files present in the output
[ ] connectionReferences carried verbatim, not authored
[ ] apisMap and connectionsMap carried verbatim
[ ] every connector the flow needs exists in the template
[ ] splitOn present on sharepoint_item triggers, absent elsewhere
[ ] no operationMetadataId anywhere
[ ] runAfter has no cycles and names only existing actions
[ ] validator run, exits clean
[ ] the user has been told the connection prompt is normal
```

## Rules

**`PLATFORM` — the package has five files, not two.**

```
manifest.json
Microsoft.Flow/flows/manifest.json          ← lists the asset folders
Microsoft.Flow/flows/<assetGUID>/definition.json
Microsoft.Flow/flows/<assetGUID>/apisMap.json          ← connector → apis resource GUID
Microsoft.Flow/flows/<assetGUID>/connectionsMap.json   ← connector → connection resource GUID
```

`connectionsMap.json` is almost certainly the "connection map" named in
`PackageFlowMissingConnectionMap`. Omit it and the import has no map to find.

**`PLATFORM` — every connector needs two GUID-keyed manifest resources**: a
`Microsoft.PowerApps/apis` (`configurableBy: System`) and a `Microsoft.PowerApps/apis/connections`
(`configurableBy: User`) that `dependsOn` it. The flow resource `dependsOn` all of them. The
`apis/connections` resource is what makes the import UI offer a connection picker.

**`PLATFORM` — two different fields are both called `connectionName`, and they differ.**

| Where | Value |
|---|---|
| `connectionReferences` **key** | the connector API name — `shared_sharepointonline` |
| `connectionReferences.<key>.connectionName` | an **opaque per-connection id**, e.g. a 32-hex string or `shared-<api>-<guid>` |
| `actions.*.inputs.host.connectionName` | the connector API name again, matching the key |

The middle one is the one that cannot be authored. Two connections in one real export used two
different formats — there is no pattern to generate.

**`PLATFORM` — `splitOn` on `sharepoint_item` triggers only.** A SharePoint item trigger returns
an array; without `splitOn` the flow fires once per batch instead of once per item. The literal
form is `"@triggerOutputs()?['body/value']"`. Power Apps and child triggers do not return arrays —
do not add it there.

**`PLATFORM` — never generate `operationMetadataId`.** Zero occurrences in a real export, on the
trigger or on any action at any nesting level.

**`PLATFORM` — never author `definition.metadata`.** It exists once, at definition level, and holds
tenant-specific values including the creator's user GUID and tenant GUID. Carry it from the
template or omit it.

**`PLATFORM` — `runAfter` decides execution order, not key order.** Every name in a `runAfter` must
be an existing action, and the graph must be acyclic. The first action has `runAfter: {}`.

**`PLATFORM` — the connection prompt at import is normal, not a failure.** A legacy package
*requires* connections to be remapped by hand; solutions avoid this with environment variables,
legacy packages do not. Tell the user:

- *"Import asks you to pick connections"* → expected. Pick them.
- *"A grey X you cannot resolve, or `PackageFlowMissingConnectionMap`"* → a real failure.

A skill that calls the prompt a bug sends people hunting something that is not there.

**`HOUSE` — one child flow for notifications.** When more than two flows send mail, make one child
flow they all call rather than duplicating the logic.

**`HOUSE` — guard before acting.** Validation belongs in the flow, not only in the app. A flow that
trusts its inputs because the app validates them fails the first time anything else calls it.

## Validation gate

Run `python scripts/validate_flow.py <package-dir-or-zip>`. If it fails, fix and re-run. Do not
present output to the user until the validator exits clean.

**Know what this validator cannot tell you.** It checks structure against a real export. It cannot
confirm the package imports into your tenant, because that depends on values only that tenant
holds. Seventeen compiling screens back the Power Apps validator; this one is backed by one
observed export. Say so when handing over, and treat the first import as a test.
