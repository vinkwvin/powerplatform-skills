ทำไมผมถึงทำอันนี้

เริ่มจากสองเรื่องที่พี่ ๆ บ่นตรงกัน และผมก็เจอเหมือนกันทุกครั้ง:

ปัญหาข้อ 1 ใช้เวลาขึ้น Power Apps เยอะ กว่าจะเลื่อนแต่ละกล่องได้แต่ละอัน
ปัญหาข้อ 2 Claude มันยัง generate Power Apps ไม่เก่ง ต้อง prompt เยอะ ๆ ตีงานกลับไปมานาน กว่าจะได้ YAML code ที่ไม่ error

สองข้อนี้เป็นเรื่องเดียวกัน

ที่ Claude generate ไม่เก่ง ไม่ใช่เพราะมันเขียน code ไม่เป็น แต่เพราะมันไม่รู้กฎเฉพาะของ Power Apps ที่เราต้องเจ็บตัวเองถึงจะรู้ — control type ไหนมีอยู่จริงบ้าง เวอร์ชันต้องเป็นเลขอะไร property เรียงยังไง ค่าแบบไหนทำให้ YAML พังทั้งไฟล์

พอไม่รู้ มันก็เดา และคำตอบที่เดามาจะดูถูกต้องเสมอ — ชื่อ control ที่ฟังดูมีจริง property ที่ฟังดูสมเหตุสมผล เราถึงไม่รู้ตัวจนกด paste แล้ว error นั่นแหละคือรอบที่กินเวลาเรามากที่สุด

ผมเลยไม่ได้ไปนั่งสอนมันใหม่ทุกแชท แต่ไปวัดกฎจากของจริงที่ compile ผ่านแล้ว แล้วใส่ไว้ใน skill ให้มันรู้ตั้งแต่ยังไม่เริ่มพิมพ์

กฎทุกข้อวัดมาจากของที่ทำงานได้จริง ไม่ได้มาจากเอกสาร

· 17 หน้าจอที่ compile ผ่าน Studio — 2,830 controls, 2,847 property blocks
· 10 SharePoint lists, 131 columns ที่ใช้งานอยู่จริงใน production
· flow package ที่ export ออกมาจาก tenant ของเราเอง

กฎข้อไหนมีตัวเลขแปะอยู่ แปลว่ามันไม่ใช่ความเห็น และตอนที่เอกสาร convention ของเราขัดกับไฟล์ที่ shipped ไปแล้ว — ไฟล์ชนะ เอกสารโดนแก้ (มี 7 ค่าที่เอกสารเราสั่งไว้ แต่ไม่ปรากฏเลยสักครั้งใน 17 หน้าจอ)

วิธีใช้

ใช้ยังไงให้ token ไม่หมดก่อนงานเสร็จ

พี่ ๆ ใช้ Pro plan เพราะฉะนั้นข้อนี้สำคัญพอ ๆ กับความถูกต้อง

1. หนึ่ง stage ต่อหนึ่งแชท

เปิดแชทใหม่ทุกครั้งที่ขึ้น skill ตัวใหม่ ไม่ใช่เรื่องความเป็นระเบียบ แต่เป็นเรื่อง budget ตรง ๆ — ถ้าเอาการสัมภาษณ์ requirement กับการสร้างของสามอย่างมาอยู่แชทเดียวกัน context จะถูกกินไปกับเรื่องที่ stage หลัง ๆ ไม่ได้ใช้ และคุณภาพจะตกก่อนที่ token จะหมดด้วยซ้ำ

2. พก solution-spec.yaml ข้ามแชท — แนบเป็นไฟล์ อย่า paste ทั้งก้อน

แนบไฟล์ไป แล้วพิมพ์ว่า “สร้าง SharePoint list ตาม spec นี้” พอ ไม่ต้องเล่าระบบใหม่ ไม่ต้อง paste YAML ทั้งอันลงในช่องแชท

3. prompt สั้น ๆ ก็พอ กฎอยู่ใน skill แล้ว

ไม่ต้องเขียน prompt ยาว ๆ อธิบายว่าอยากได้ YAML แบบไหน ไม่ต้องแปะ convention ไม่ต้องเตือนมันเรื่อง property ordering — ทุกอย่างนั้นอยู่ใน skill แล้ว การเขียนซ้ำคือการจ่าย token ซ้ำ

4. มีอะไรจะแก้ บอกให้ครบในรอบเดียว

สะสมสิ่งที่จะแก้ให้ครบแล้วส่งไปทีเดียว ประหยัดกว่าส่งทีละข้อสามรอบมาก และผลลัพธ์มักจะดีกว่าด้วย เพราะมันเห็นภาพรวมของสิ่งที่เราต้องการ

ถ้า validator เตือนขึ้นมาเป็นสิบบรรทัดเพราะโปรเจกต์นี้ใช้สีกับขนาดคนละชุด — อย่าไปแก้อะไร และอย่าเริ่มชินกับการมองข้าม warning ให้เปิดไฟล์ project-style-override.md ที่แนบมา แล้ววาง prompt ในนั้นตอนเริ่มแชท มันจะตั้งค่าสไตล์ของโปรเจกต์นี้ให้ โดยไม่ต้องแตะ skill เลย

ทุก skill จะรัน validator ให้ก่อนส่งงาน และมันจับได้เยอะจริง ๆ — control type ที่ไม่มีอยู่จริง, property ที่เรียงผิด, ค่าที่ทำให้ YAML พัง, ขนาดที่หลุดจากชุดที่วัดมา

แต่มันอ่านแค่ตัวหนังสือ มันไม่ได้คำนวณ layout มันไม่มีทางรู้ว่ากล่องนี้เตี้ยเกินกว่าของที่อยู่ข้างใน หรือเส้นขอบของลูกโดนขอบของพ่อบังอยู่

เรื่องนี้ผมพลาดเอง และมันทำให้เสียเวลาไป 3 รอบ

ตอนแรกผมให้ validator ขึ้นข้อความว่า “Clean. Safe to paste into Power Apps Studio.” ซึ่งมันเคลมเกินจริง เพราะสิ่งที่มันพิสูจน์ได้จริง ๆ มีแค่ “ไฟล์นี้ parse ผ่าน”

ผลคือผมรัน validator ผ่าน แล้วก็เชื่อมัน — สามรอบติด ทั้งที่หน้าจอออกมาเพี้ยนทุกรอบ ตอนนี้แก้แล้ว มันจะขึ้นว่า “No errors found. This should PARSE and paste.” แล้วตามด้วยรายการที่มันไม่ได้ตรวจ ทุกครั้ง

✓ มันตรวจให้

  • control type และเวอร์ชันมีจริงไหม
  • property เรียงถูกไหม
  • ค่าที่ต้องใส่ block scalar
  • X/Y ที่ไม่ควรมี
  • property ที่หน้าจอต้องมี
  • enum member ที่ยังไม่มีใครยืนยัน

✗ มันตรวจไม่ได้

  • กล่องสูงพอใส่ของข้างในไหม
  • เส้นขอบโดนพ่อบังหรือเปล่า
  • =Parent.Width ล้นพ่อที่มี padding
  • อะไรก็ตามที่ขึ้นกับข้อมูลจริงตอน run

เพราะฉะนั้น: paste เข้าไป ดูหน้าจอ แล้วบอกมันว่าเห็นอะไร

การบอกว่า “กล่องนี้เตี้ยไป ตัวหนังสือล้น” หนึ่งรอบ เร็วกว่านั่งเดากับมันสามรอบเยอะมาก — และรอบนั้นคือรอบที่ตาพี่ ๆ ทำได้ดีกว่ามันแน่นอน

prompt เต็ม ๆ อยู่หน้าถัดไป และในไฟล์ team-quick-feedback.md Claude จะเขียนบันทึกสั้น ๆ ออกมาว่าอะไรต้องแก้บ้าง เซฟแล้วส่งมาทาง Teams จบ

ต้องท้ายแชทเท่านั้น แชทยาว ๆ จะถูกย่อความ แล้วสิ่งที่เหลือรอดคือสรุปที่ฟังดูสมเหตุสมผล มากกว่าที่ถูกต้อง ถามวันศุกร์ถึงงานวันอังคาร จะได้เรื่องแต่งที่มีผิวสัมผัสของข้อเท็จจริง

และอย่ากรองก่อนส่ง — อย่าคิดแทนว่าเรื่องนี้สำคัญพอไหม มีคนบอกไปหรือยัง หรือเป็นความผิดตัวเองหรือเปล่า ส่งมาเถอะครับ ตัดสินใจเป็นงานผม และผมทำได้ดีกว่ามากตอนมีห้ารายงาน มากกว่ามีอันเดียว

ไม่ต้องรอผม

สี ขนาดฟอนต์ ระยะห่าง prefix ตัวแปร — พวกนี้เป็นธรรมเนียมของทีม ไม่ใช่กฎของแพลตฟอร์ม เปลี่ยนได้โดยไม่ต้องรอใคร ใช้ prompt ในไฟล์ project-style-override.md

อยากรู้ว่าที่เตือนมามีอันไหนพังจริงบ้าง พิมพ์ว่า “validate with --platform-only แล้วเทียบสองรอบให้ดู” อะไรที่หายไปคือเรื่องสไตล์ อะไรที่ยังอยู่คือเรื่องที่ Studio จะปฏิเสธจริง

และผมจะบอกด้วยว่าเรื่องไหนผมไม่ได้แก้ และเพราะอะไร — คนที่ส่งมาสองครั้งแล้วไม่เห็นอะไรเกิดขึ้น จะเลิกส่ง แล้วผมก็เสียข้อมูลนั้นไปถาวร
